# MR mentor

Читатель — аналитик или джун. Код за него пишет ИИ. Перед отправкой сеньору читатель проверяет MR: что
сделано, правильно ли разложено по слоям, где бизнес-правило, где слабые места, что расходится со спекой,
нет ли лишнего. Попутно учится читать код: сначала картина и путь запроса, потом файлы и детали.

Ты пишешь **факты** в JSON, страницы из них строит скрипт. Каждый факт — один раз и с id: требование,
кусок кода, замечание, решение, тест. Вердикт, чек-лист, таблицы, граф вызовов, главы и задания на
странице скрипт выводит сам — поэтому один факт не может разойтись сам с собой.

- Формат JSON — `references/schema.md`.
- Что писать в каждом поле — `references/fields.md`. Открывай раздел, когда дошёл до этого поля.
- Где искать слабые места по роли файла — `references/file-checklists.md`.

## Что нужно

- Локальный клон репозитория MR и `git`. Скрипт сам берёт диффы из клона и проверяет якоря.
- Python 3.10 или новее, без сторонних библиотек.
- Доступ к MR: GitLab MCP-сервер с чтением MR и GraphQL или CLI `glab`. Нет ни того, ни другого —
  попроси пользователя вставить описание MR и обсуждения.
- Стек: роли слоёв и чек-листы рассчитаны на Kotlin/Java, Spring и раскладку `application` /
  `core/ports` / `core/services` / `infrastructure`. На другом стеке разбор работает, но роли слоёв
  на карте и в графе останутся пустыми — скажи об этом пользователю.
- Страницы и тексты — на русском.

## Ход работы

Скопируй чек-лист в ответ и отмечай по ходу:

```
- [ ] 1. Материал: MR, статус, дифф, задача, спека, код вокруг изменений
- [ ] 2. Факты: требования → контекст → куски → замечания → пробы (≥3) → решения и тесты
- [ ] 3. Маршрут: план глав с заданиями → путь запроса → механизм → картина → поля обучения
- [ ] 4. Рендер без «ошибка:» и «проверка:»
- [ ] 5. Сдача: два пути, открыть ревью, вердикт одной строкой
```

## Как писать

1. **Термин — с расшифровкой при первом упоминании.** Каждый термин задачи и аббревиатура из вердикта,
   контекста, пути запроса и решений — в `context.terms` или `glossary`: рендер подсветит его подсказкой
   там, где он встретился впервые. Валидатор ловит аббревиатуры без расшифровки.
2. **Предметная область, а не синтаксис.** «Фасад отсекает чужой заказ до расчёта скидки». Внутренний
   класс называй, только если читатель увидит его в графе или диффе.
3. **Конкретика.** Имена из кода и значения: «промокод `SALE10`», «`422`», «таймаут 3 с».
4. **Клиентских данных нет нигде**, даже тестовых: заглушки `<номер клиента>`, `<ФИО>`. Диффы скрипт
   чистит сам, а твой текст проверяет валидатор.
5. **Код MR, а не его история.** Ход работы, треды, коммиты — только в `evidence_private` решения,
   на страницу это не попадает.
6. **Спека — её словами:** «спека, операция 1, шаг 7.1». Ссылка — в `meta.mr.spec`.
7. **Проверь каждое утверждение по коду.** Правдоподобная догадка хуже пропуска.

## Шаг 1. Собрать материал

1. MR: название, описание, ветки, обсуждения, живой статус — Draft, одобрения, пайплайн, открытые треды
   и дата среза. Статус кладётся в `meta.mr.status`, его показывает строка чек-листа «CI и ревью».
   `meta.mr.state` — `opened` или `merged`: у влитого MR вердикт — «влит», а не «можно мержить».
   - GitLab MCP: в Claude Code инструменты сервера называются `mcp__<сервер>__<инструмент>`, например
     `mcp__gitlab__get_merge_request`. Обсуждения большого MR бери GraphQL-запросом с обрезкой тел.
     Статус: `mergeRequest { draft approvalsRequired approvedBy{nodes{username}} headPipeline{status}
     discussions{nodes{resolvable resolved}} }`; открытый тред — `resolvable && !resolved`.
   - Без MCP: `glab mr view <iid> --comments` и `glab api graphql -f query='…'` с тем же запросом.
2. Код — локальный клон, свежий `git fetch`. `meta.repo` — путь к клону, `meta.range` — диапазон
   `origin/<целевая ветка>...HEAD` на ветке MR или `<merge-base>...<ветка>`. Оба поля обязательны:
   без них валидатор не пустит дальше. Дифф: `git diff --numstat <range>`.
3. Задача из трекера — условия списком. Спека, если есть. `CLAUDE.md`/`README` репозитория — раскладка
   пакетов.
4. Код вокруг изменений: метод целиком, кто его вызывает до точки входа.

## Шаг 2. Записать факты

Поля — в порядке чек-листа, правила каждого — в `references/fields.md`:

1. `requirements`, `context` — что просит задача и без чего не понять вердикт.
2. `chunks` — главное: все значимые изменённые строки `src/main` попадают в куски до 45 строк. Одна и та
   же правка в нескольких файлах — `same_as`.
3. `findings` — слабые места, каждое один раз; `probes` — минимум три пробы на старых данных, кривых
   и пустых входах.
4. `decisions`, `tests`.
5. `plan` с заданиями `check` в каждой главе, `trace`, `mechanism`, `picture`, `example`,
   `before_after`, `lessons`, `quiz`, `service`.

Внутренние id (F-…, T…) в тексте не пиши — читатель их не видит.

## Шаг 3. Проверить и сдать

1. Сохрани JSON: `<папка результатов>/<repo>-<iid>/<repo>-<iid>.json`. Папку называет пользователь;
   не назвал — `./mr-mentor-result`.
2. Запусти `python3 ${CLAUDE_SKILL_DIR}/scripts/render.py <json>`. Скрипт сначала валидирует:
   - `ошибка:` — страницы не нарисованы. Исправь JSON и запусти снова.
   - `проверка:` — страницы есть, но в тексте пересказ замечания, кусок без `how`, строки вне кусков или
     история. Тоже исправь и запусти снова, а не обходи.
   - Повторяй, пока обоих видов строк не останется.
3. Скрипт пишет `<repo>-<iid>.html` — ревью и `<repo>-<iid>-learn.html` — обучение. Что куда выводится,
   решает скрипт.
4. Сдача: оба пути, открой ревью (`open` на macOS, `xdg-open` в Linux), вердикт одной строкой.

## Не делать

- Не править код MR: нашёл проблему — замечание.
- Не публиковать HTML и не писать в GitLab без просьбы. Не вставлять секреты из логов CI.
- Не писать вердикт, чек-лист, таблицы требований, рисков и тестов руками — их строит скрипт.
